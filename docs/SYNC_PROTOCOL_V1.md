# Протокол синхронизации v1 — Lampa Sync Pro

**Состояние:** спецификация v1, серверные таблицы и RPC реализованы. [Точные параметры опубликованного API](API_V1.md). Клиент и реальный E2E ещё не реализованы. Опирается на [аудит](SOURCE_AUDIT.md).

## 1. Главные инварианты

1. **Серверное состояние первично для межустройственных данных**, локальное хранилище — рабочий кэш + очередь. При недоступности сервера просмотр не блокируется.
2. **Никакой синхронизации всего localStorage.** Не читать/передавать пароли, cookie, `rezka_bridge_token`, ключи CUB/Trakt, proxy-конфиги, заголовки авторизации, stream URL и URI торрентов с приватными tracker passkey.
3. Подтверждённая позиция просмотра отдельна от факта **открытия** карточки или нажатия кнопки воспроизведения.
4. Торрентный `infohash` и `file_index/path` обозначают **источник**, но не идентичность фильма/эпизода.
5. Полное окончание эпизода и ручное «снять просмотрено» — отдельные события, не вывести сброс из `time=0`.
6. Из двух устройств нельзя вычислять свежесть **только по времени устройств**. Нужны серверные `revision` и `event_id`.
7. Данные HDRezka из Netlify не импортируются в Supabase до проверки контракта и разрешённых provider IDs.

## 2. Три уровня данных

### A. Контент

- `media_key` — проверяемый `tmdb:tv:<id>`, `tmdb:movie:<id>`, `imdb:<id>` или `kinopoisk:<id>`; предпочтителен TMDb, тип `tv/movie` обязателен.
- `media_aliases` — только подтверждённые идентификаторы, полученные из одной Lampa-карточки; **не связывать совпадение только по названию**.
- `episode_key` — для сериала `s<season>:e<episode>`; для фильма специальное значение `movie`.
- Если канонический ID отсутствует, использовать `provider:rezka:<page-id>` в изолированном пространстве, не объединять автоматически с TMDb.

### B. Логический прогресс

- `watched_state`: `unknown | in_progress | completed | reset`.
- `last_confirmed_position`, `duration_seconds` относятся к последнему **подтверждённому** сеансу данного источника.
- `resume_pointer` по пользователю/карточке указывает на эпизод/источник последнего подтверждённого сеанса.
- Ручная массовая отметка NUM является явным событием `marked_complete`/`marked_unwatched` для каждого эпизода; оно не должно возникать из фоновой синхронизации без подтверждения.

### C. Источник

`source_kind`: `torrent | hdrezka | other_online`.

- Торрент: `infohash`, `file_index`, `file_path`, опционально отображаемое имя раздачи. При отсутствии источника на новом устройстве возможен новый запрос файла TorrServer. **Не хранить magnet URL целиком, URL потока или торрент-пароли**.
- HDRezka: `page_id/url`, `provider_season_id`, `provider_episode_id`, `translator_id`, `voice_label` (необязательно). Никаких `stream`, cookie, bridge-token.
- Два источника одного эпизода имеют отдельные записи позиции, чтобы поздняя запись от HDRezka не затирала позицию TorrServer.

## 3. Минимальная логическая схема БД

| Таблица | Основное назначение | Ключ |
|---|---|---|
| `sync_devices` | Список устройств владельца, состояние подключения | `user_id + device_id` |
| `sync_heads` | Текущая серверная ревизия владельца для атомарного курсора | `user_id` |
| `watch_state` | Просмотрено/не просмотрено по эпизоду и владельцу | `user_id + media_key + episode_key` |
| `source_progress` | Прогресс для конкретного источника эпизода | `user_id + media_key + episode_key + source_key` |
| `resume_pointers` | Последний подтверждённый источник и эпизод карточки | `user_id + media_key` |
| `sync_events` | Журнал изменений, идемпотентность и удаления | `user_id + event_id` unique |

Везде обязательны `user_id UUID`, `server_revision BIGINT` и `updated_at TIMESTAMPTZ` **со стороны сервера**. Для `source_progress` допустима дополнительная `playback_session_id UUID`, для `sync_events` — `device_seq BIGINT` и `base_revision BIGINT`. Реальная SQL-схема зафиксирована в [миграциях Supabase](../supabase/migrations/).

## 4. Логические операции API

Это контракт v1. Физически его можно реализовать через Supabase PostgREST + транзакционные RPC-функции, либо Edge Functions. До тестов **не утверждать конкретные URL как работающие**.

### Загрузка

- `bootstrap()`: Auth → получение актуальной ревизии и снимка, затем без потери данных слияние с локальной очередью.
- `pull(since_revision, limit)`: только изменения после курсора, вместе с tombstones; страничный ответ содержит `next_revision` и `has_more`.
- `getResume(media_key)`: состояние/источник для отображения кнопки без выгрузки всей истории.

### Отправка

- `push(events[], expected_revision)`: пачка событий (лимиты на размер/количество), атомарное применение через серверную транзакцию.
- Каждое событие имеет уникальный `event_id`. Повторная отправка того же ID возвращает прежний результат, а не удваивает эффект.
- Если `expected_revision` устарела, сервер возвращает `CONFLICT` и актуальный курсор. Клиент сначала подтягивает изменения и применяет правило слияния; **не перезаписывает удалённо то, что не видел**.

### Пример события (поля протокола, не готовое API)

```json
{
  "schema": 1,
  "event_id": "c91977c9-ea6e-40ae-9e84-7738b1c34508",
  "device_id": "bdab426a-e59a-4c2d-ae3b-5718f8645d1e",
  "device_seq": 42,
  "playback_session_id": "5495dc65-bb78-4ce3-8b49-894bf6c4d6d3",
  "base_revision": 123,
  "kind": "progress",
  "media_key": "tmdb:tv:1000",
  "episode_key": "s2:e5",
  "source_kind": "torrent",
  "source_recipe": {
    "infohash": "0123456789ABCDEF0123456789ABCDEF01234567",
    "file_index": 4,
    "file_path": "Season 2/E05.mkv"
  },
  "position_seconds": 1120,
  "duration_seconds": 2700
}
```

Значения в примере — **фиктивные**, не реальная история.

## 5. Типы событий и конфликты

- `started` — начало воспроизведения, только после подтверждения реального плеера.
- `progress` — изменение позиции в рамках одной сессии.
- `paused`/`stopped` — финальный checkpoint.
- `completed` — завершение или достижение согласованного порога (первоначально 90%).
- `marked_complete`/`marked_unwatched` — явное действие пользователя.
- `deleted` — явное удаление с tombstone; отсутствие записи в локальном кэше удалением не считается.

**Правила:**

1. `event_id` обеспечивает дедупликацию; `device_seq` фиксирует порядок событий одного устройства.
2. `sync_heads` блокируется в транзакции на время применения пачки; при успехе события получают возрастающие серверные ревизии.
3. В одной `playback_session_id` последний подтверждённый checkpoint заменяет предыдущий; позиция вправе **уменьшаться** при ручной перемотке.
4. Поздно пришедшие `paused/stopped/progress` от старого сеанса не вправе перезаписать более новый принятый `resume_pointer`. Старый источник может сохранить собственный checkpoint, но не стать активным.
5. `completed` не может быть отменён обычным `progress` из другой сессии. Снятие отметки требует явного `marked_unwatched`.
6. При конфликте на один эпизод приоритет не определяется одним `client_updated_at`; клиент получает конфликт, сохраняет локальную очередь и повторяет с учётом серверного состояния. Безопасный fallback — **не менять состояние автоматически**, показать последнее подтверждённое.
7. `deleted` имеет отдельную ревизию и хранится достаточно долго, чтобы старые устройства не восстановили удалённую запись при подключении.
8. Для разных source_kind прогресс не смешивать; общий `resume_pointer` обновлять только корректным новым подтверждённым сеансом.

## 6. Алгоритм клиента

1. `appready`: восстановить локальную очередь, загрузить snapshot/delta, затем осторожно применить изменения к поддерживаемым объектам Timeline (без изменения лишних ключей).
2. `player create`: сохранить контекст карточки + источника в памяти, но не создавать прогресс.
3. `player start`/подтверждённый event плеера: создать `playback_session_id`; `started` в локальную очередь.
4. `timeupdate`: записывать локальный checkpoint; отправлять не чаще 20–30 сек и при паузе/закрытии. Не зависеть от доставки последнего события в момент выгрузки приложения.
5. Открытие карточки: подтянуть delta при наличии сети, показать **одну** кнопку продолжения на основе server resume_pointer; если источника нет — предложить обычный выбор, не запускать непроверенный файл.
6. `app foreground`/возврат сети: дослать очередь и получить новые изменения.
7. Для энергосбережения не держать обязательный WebSocket. Realtime — оптимизация после MVP; достаточно pull при запуске/активности и перед возобновлением.
8. Дублирующиеся плеерные события из NUM/HDRezka/ядра должны иметь единый source/session context, чтобы не возникало двух cloud-прогрессов.

## 7. Безопасность Supabase

- Единый владелец данных аутентифицирован через Supabase Auth, каждое устройство получает **собственную сессию пользователя**.
- На TV лучше отдельное короткоживущее спаривание с подтверждением на уже авторизованном устройстве; детали Auth-flow отдельно проверяются перед реализацией.
- Клиентский JavaScript может использовать только publishable key и пользовательский JWT. Никогда не использовать `service_role`/secret-key в Lampa.
- Таблицы `public` закрыты RLS по `(select auth.uid()) = user_id` с `USING` и `WITH CHECK` для обновлений; доступ выдаётся только `authenticated`.
- Открытие через Data API требует обоих условий: минимальные `GRANT` и корректные RLS. Публичные SQL-функции по умолчанию нельзя считать защищёнными.
- Поля, размеры payload и content/source enums проверяются **на сервере**; клиентская проверка не заменяет SQL constraints.
- CORS/HTTPS для webview/Android TV/iOS обязательны; пользовательские JWT/ключи не выводятся в лог.

Официальная документация: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Securing the Data API](https://supabase.com/docs/guides/api/securing-your-api).

## 8. Миграция и откат

- До deployment: снимок схемы, dump существующих таблиц целевого проекта, фиксация SHA плагинов.
- Новые таблицы с префиксом или в отдельном `sync`/выделенном API schema; не менять действующие базы.
- Флаги функций: `capture_enabled`, `cloud_pull_enabled`, `cloud_push_enabled`, `timeline_apply_enabled`, `hdrezka_integration_enabled`. По умолчанию `timeline_apply` и HDRezka **выключены**.
- Первая установка запускается в режиме read-only/dry-run. Сравнить локальные и облачные данные, исключить перезапись CUB и Netlify.
- Rollback: выключить флаги, откатить версию клиентского JS; облачные данные сохраняются для разбирательства. Удаление таблиц не является быстрым откатом.

## 9. Ограничения MVP

- **Не гарантируется** сохранение точной позиции внешнего плеера на всех платформах, пока не проверены события.
- Переключение между разными TorrServer/торрентами может требовать ручного поиска источника.
- Без надёжного crosswalk не объединяем списки HDRezka и TMDb по названию.
- CUB/Trakt не получают и не отдают эти новые source-specific таймкоды автоматически.
- Схема v1, тесты и реальный E2E на TV/Mac/iOS должны быть завершены до публикации плагина в магазине.
