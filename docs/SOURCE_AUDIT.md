## Проверенные конкретные контракты

### NUM Series Pro 2.0.5

- Строки 433–477: `setWatched`/`undoBulk` обновляют существующие объекты Timeline; успешное сохранение в TorrServer зависит от включённого TrackTimecode, `torrent_hash`, индекса файла и известной длительности.
- Строки 572–605: обработчики `Lampa.Timeline.listener.update/read`; UI берёт значения `hash,time,duration,percent,updated`.
- Строки 275–317: вычисление кандидата продолжения по сгруппированным сезонам/сериям; в торрентах один эпизод может встречаться в нескольких файлах/раздачах.
- В самом NUM нет отдельного облачного хранилища; связи `timeline.hash` с каноническим ID сериала для разных устройств необходимо проверять отдельно.

### HDRezka

- Строки 598–642: `GET/POST /v1/watch/progress` с `X-Rezka-Bridge-Token` на пользовательский Netlify bridge; ответ `GET` содержит массив `items`.
- Строки 643–731: сериализация запуска содержит `url` страницы, `season`, `episode`, `translator`, `voice`, `position`, `duration`, `status`, **а также `stream`**. Повторять передачу `stream` в Supabase запрещено: там может быть подписанная/временная ссылка.
- Строки 975–1024: выбранную озвучку, эпизод и позицию восстанавливает сам плагин через существующий Netlify progress.
- ID `season.id` и `episode.episode_id` относятся к провайдеру: не предполагать, что это номера SxxExx. Карточки коллекций `source: custom` могут не иметь достоверного TMDB ID.
- Прямого стабильного `window` API для передачи прогресса стороннему синхронизатору в проверенном коде не обнаружено. Для поздней интеграции нужен отдельный безопасный адаптер/событие, а не перехват токена шлюза.

### ARST113 Watch Resume

- Строки 934–970: последний эпизод и при 90% переход к следующему из **доступного** плейлиста.
- Строки 1621–1655: сначала штатные `Lampa.Torserver.viewed/viewedSet`, затем fallback `/viewed`.
- Строки 1840–1899: серверный TrackTimecode участвует в восстановлении только при включённой настройке и при отсутствии более сильной локальной позиции Timeline.
- Строки 1157–1234: кнопка появляется на **карточке сериала при наличии собственной записи**. Одной серверной истории TorrServer для её появления недостаточно.
- Поддержка Lampac Online в этой реализации не равнозначна нативной поддержке HDRezka.

### 0x3654 marks

- Сервер: `GET /m/<secret>/` и `POST /m/<secret>/`; записи `list/card/updated/deleted`.
- README: boot-pull, sync-up, watchdog через 5 минут, tombstone для снятия отметок.
- LWW по времени клиента может затирать поздно доставленные данные или конфликтующие просмотры. Для собственного проекта заменить на **серверную ревизию, session_id и тип события**.

### zxkill Lampa Sync Player

- Ключи локального Lampa `file_view`, `file_view_<profile>` и история действительно участвуют в синхронизации.
- Репликация всего localStorage опасна для `rezka_bridge_token`, авторизационных данных, настроек устройства, URI TorrServer и конфликтов со штатным CUB. **Этот метод не применять.**
- PHP, FFmpeg и HLS не требуются для метаданных просмотра.

## Что нужно подтвердить на реальном устройстве до записи в облако

1. Как формируется `Timeline.hash` и меняется ли он при выборе другой раздачи того же эпизода.
2. Какие реальные поля присутствуют в `Lampa.Player.listener` и Timeline на Android TV, macOS, iOS.
3. Доступен ли один TorrServer со всех устройств; что происходит при смене адреса/хеша/индекса файла.
4. Возвращает ли внешний плеер реальную позицию на каждой платформе или только факт запуска.
5. Может ли HDRezka однозначно связать свои provider IDs с TMDB; иначе сохраняем раздельные идентичности.
6. Не восстанавливает ли CUB более старый Timeline после нашего импорта.
7. Возможность HTTPS, CORS, Auth JWT и фоновой очереди в каждой сборке Lampa.
8. Стабильность порядка событий при выходе из приложения, особенно на iOS.

## Результат аудита

Рекомендуется отдельный **Lampa Sync Pro** с узкими, версионированными адаптерами. Первая версия: TorrServer + NUM, синхронизация **подтверждённых** просмотров по каноническому ID. HDRezka добавляется после проверки адаптера и механизма согласования; существующая Netlify-синхронизация остаётся неизменной. CUB/Trakt сохраняют собственные функции.
